## AI-Based Fake News Detection System

## 1. Introduction

### 1.1 Purpose

This Software Requirements Specification defines the functional and non-functional requirements for an AI-Based Fake News Detection System. The document is intended for project supervisors, examiners, developers, testers, and project stakeholders. It establishes what the system should do, how it should behave, and the constraints that guide design and implementation.

### 1.2 Document Scope

This SRS covers:

- User-facing web application requirements.
- Backend API requirements.
- Database and data storage requirements.
- AI/ML model requirements.
- Admin and reporting requirements.
- Security, performance, usability, reliability, and maintainability requirements.
- Acceptance criteria and requirement traceability.

### 1.3 Product Scope

The system will allow users to submit news content and receive an AI-assisted prediction indicating whether the content is likely to be real, fake, misleading, or suspicious. The system will support user accounts, prediction history, administrative analytics, model version tracking, and reporting.

## 2. Overall Description

### 2.1 Product Perspective

The product is a web-based AI system with four major layers:

- Frontend web interface.
- Backend REST API.
- PostgreSQL database.
- AI/ML inference and training pipeline.

The system may be deployed as a set of independent services or as a monolithic backend with modular internal components for the final-year project prototype.

### 2.2 Product Functions

Major system functions include:

- User registration and authentication.
- News text submission.
- Optional URL-based news extraction.
- NLP preprocessing.
- Fake news classification.
- Confidence score calculation.
- Explanation generation.
- Prediction history.
- Admin analytics.
- Model version management.
- Report generation.

### 2.3 User Classes

| User Class | Description | Main Permissions |
|---|---|---|
| Guest User | Visitor who has not logged in. | Register, login, view public pages if available. |
| Registered User | Authenticated user who checks news content. | Submit news, view own results, view own history. |
| Admin User | Authorized administrator. | View analytics, manage datasets, inspect model versions, generate reports. |
| Project Evaluator | Supervisor or examiner reviewing the project. | View demo, review reports, inspect evaluation results. |

### 2.4 Operating Environment

Recommended operating environment:

- Client: Modern browser such as Chrome, Edge, or Firefox.
- Frontend: React.js or Next.js.
- Backend: Python FastAPI.
- Database: PostgreSQL.
- ML runtime: Python with scikit-learn and optionally Hugging Face Transformers.
- Deployment: Docker-based deployment to cloud platform or university demonstration machine.

### 2.5 Design and Implementation Constraints

- The project must be feasible within a final-year project timeline.
- Model training must match available compute resources.
- Dataset licensing must allow academic use.
- User passwords must never be stored in plain text.
- The prediction output must not be presented as absolute truth.
- The system must record the model version used for each prediction.

### 2.6 Assumptions and Dependencies

Assumptions:

- The project focuses on English-language news unless the proposal specifies otherwise.
- A labeled fake/real news dataset will be available.
- Users will access the system through a web browser.
- The first production-like prototype will prioritize text submission over complex social media integration.

Dependencies:

- Dataset availability and quality.
- Python ML libraries.
- Database availability.
- Hosting platform availability.
- Browser compatibility.

## 3. External Interface Requirements

### 3.1 User Interfaces

The system shall provide the following pages:

- Login page.
- Registration page.
- User dashboard.
- News analysis page.
- Prediction result page.
- Prediction history page.
- Admin dashboard.
- Dataset/model management page.
- Reports page.
- Profile/settings page.

UI requirements:

- Forms shall provide clear validation messages.
- Prediction results shall display label, confidence score, and explanation.
- The interface shall clearly state that predictions are AI-assisted.
- Admin pages shall be inaccessible to non-admin users.
- Pages shall be responsive for desktop and mobile screens.

### 3.2 Hardware Interfaces

No special hardware interfaces are required for the core system. Optional GPU acceleration may be used during model training if transformer-based models are selected.

### 3.3 Software Interfaces

| Interface | Purpose |
|---|---|
| Frontend to Backend API | Submit requests and receive responses. |
| Backend to Database | Store users, submissions, predictions, reports, and model metadata. |
| Backend to ML Model | Run preprocessing and inference. |
| Backend to URL Extraction Service | Extract article text from provided URLs if supported. |
| Backend to Report Generator | Produce structured project or usage reports. |

### 3.4 Communication Interfaces

- HTTPS should be used in deployed environments.
- JSON shall be used for API request and response bodies.
- JWT shall be used for authenticated API access.

## 4. System Features and Functional Requirements

### 4.1 Authentication and User Management

| ID | Requirement |
|---|---|
| FR-AUTH-01 | The system shall allow new users to register with name, email, and password. |
| FR-AUTH-02 | The system shall validate email format and password strength. |
| FR-AUTH-03 | The system shall hash passwords before storing them. |
| FR-AUTH-04 | The system shall allow registered users to log in. |
| FR-AUTH-05 | The system shall issue a secure access token after successful login. |
| FR-AUTH-06 | The system shall allow users to log out on the frontend. |
| FR-AUTH-07 | The system shall restrict protected pages and APIs to authenticated users. |
| FR-AUTH-08 | The system shall support user roles such as `user` and `admin`. |

Acceptance criteria:

- A valid user can register and log in.
- Invalid credentials are rejected.
- Passwords are not visible in database records.
- Non-admin users cannot access admin endpoints.

### 4.2 News Submission

| ID | Requirement |
|---|---|
| FR-SUB-01 | The system shall allow authenticated users to submit news text. |
| FR-SUB-02 | The system shall reject empty submissions. |
| FR-SUB-03 | The system shall enforce a maximum input length. |
| FR-SUB-04 | The system shall optionally allow users to submit a URL. |
| FR-SUB-05 | The system shall extract readable article text from supported URLs. |
| FR-SUB-06 | The system shall store each valid submission with timestamp and user ID. |

Acceptance criteria:

- Valid text input creates a stored submission.
- Empty or oversized input returns a validation error.
- URL submission fails gracefully when extraction is not possible.

### 4.3 AI Prediction

| ID | Requirement |
|---|---|
| FR-PRED-01 | The system shall preprocess submitted text before prediction. |
| FR-PRED-02 | The system shall load the active model version for inference. |
| FR-PRED-03 | The system shall classify submitted news content. |
| FR-PRED-04 | The system shall return a prediction label. |
| FR-PRED-05 | The system shall return a confidence score. |
| FR-PRED-06 | The system shall return a short explanation or key indicators. |
| FR-PRED-07 | The system shall store the prediction result in the database. |
| FR-PRED-08 | The system shall store the model version used for each prediction. |
| FR-PRED-09 | The system shall handle model loading and inference errors gracefully. |

Acceptance criteria:

- A valid submission receives a prediction response.
- Prediction record includes label, confidence, model version, and timestamp.
- Model failure returns a controlled error response.

### 4.4 Prediction History

| ID | Requirement |
|---|---|
| FR-HIST-01 | The system shall allow users to view their own prediction history. |
| FR-HIST-02 | The system shall prevent users from viewing other users' history. |
| FR-HIST-03 | The system shall allow users to view details of a previous prediction. |
| FR-HIST-04 | The system shall support pagination or filtering when history grows. |

Acceptance criteria:

- Users see only their own records.
- History shows submission date, label, confidence, and source type.

### 4.5 Admin Dashboard

| ID | Requirement |
|---|---|
| FR-ADMIN-01 | The system shall provide an admin dashboard. |
| FR-ADMIN-02 | The system shall show total users, total submissions, and prediction counts. |
| FR-ADMIN-03 | The system shall show model performance metadata. |
| FR-ADMIN-04 | The system shall allow admins to view model versions. |
| FR-ADMIN-05 | The system shall allow admins to view dataset metadata. |
| FR-ADMIN-06 | The system shall restrict admin features to admin users. |

Acceptance criteria:

- Admin dashboard loads only for admin users.
- Non-admin users receive an authorization error.

### 4.6 Dataset and Model Management

| ID | Requirement |
|---|---|
| FR-ML-01 | The system shall store metadata for each trained model. |
| FR-ML-02 | The system shall record model algorithm, version, artifact path, and metrics. |
| FR-ML-03 | The system shall identify one active model version for inference. |
| FR-ML-04 | The project shall include training scripts or notebooks. |
| FR-ML-05 | The project shall document dataset preprocessing and evaluation results. |

Acceptance criteria:

- Model version records exist for trained models.
- The backend can load the active model.
- Evaluation metrics are documented.

### 4.7 Reporting

| ID | Requirement |
|---|---|
| FR-REP-01 | The system shall support basic report generation. |
| FR-REP-02 | Reports shall include prediction counts and model performance summaries where applicable. |
| FR-REP-03 | Generated reports shall be stored or referenced in the database. |
| FR-REP-04 | The project shall include academic reports required for assessment. |

Acceptance criteria:

- Report metadata is stored after report generation.
- Admin or authorized user can access generated reports.

## 5. Non-Functional Requirements

### 5.1 Performance

| ID | Requirement |
|---|---|
| NFR-PERF-01 | The system should return text prediction results within 2-5 seconds after model warm-up. |
| NFR-PERF-02 | The API should handle common validation failures without noticeable delay. |
| NFR-PERF-03 | Long-running model training shall be performed offline, not during user prediction requests. |

### 5.2 Security

| ID | Requirement |
|---|---|
| NFR-SEC-01 | Passwords shall be hashed using bcrypt or Argon2. |
| NFR-SEC-02 | Protected APIs shall require authentication. |
| NFR-SEC-03 | Admin APIs shall require admin authorization. |
| NFR-SEC-04 | User input shall be validated and sanitized. |
| NFR-SEC-05 | Secrets shall be stored in environment variables. |
| NFR-SEC-06 | CORS shall be restricted to approved frontend origins in production. |
| NFR-SEC-07 | Prediction endpoints should include rate limiting in production. |

### 5.3 Usability

| ID | Requirement |
|---|---|
| NFR-USE-01 | The user interface shall be understandable by non-technical users. |
| NFR-USE-02 | The prediction result shall be visually clear and not overloaded with technical terms. |
| NFR-USE-03 | The system shall provide helpful error messages. |
| NFR-USE-04 | The design shall be responsive across common desktop and mobile screen sizes. |

### 5.4 Reliability

| ID | Requirement |
|---|---|
| NFR-REL-01 | The system shall handle empty input, invalid URLs, and model errors gracefully. |
| NFR-REL-02 | The backend shall log important errors for debugging. |
| NFR-REL-03 | The database schema shall preserve relationship integrity through foreign keys. |

### 5.5 Maintainability

| ID | Requirement |
|---|---|
| NFR-MAIN-01 | The codebase shall use modular structure for frontend, backend, and ML logic. |
| NFR-MAIN-02 | API contracts shall be documented. |
| NFR-MAIN-03 | The model training workflow shall be reproducible. |
| NFR-MAIN-04 | Configuration shall be separated from source code. |

### 5.6 Accuracy and Model Quality

| ID | Requirement |
|---|---|
| NFR-ML-01 | The project shall evaluate models using accuracy, precision, recall, F1-score, and confusion matrix. |
| NFR-ML-02 | The project shall compare at least one baseline model with the selected final model. |
| NFR-ML-03 | The project shall document false positives and false negatives. |
| NFR-ML-04 | The system shall not claim perfect truth verification. |

## 6. Data Requirements

### 6.1 Main Data Entities

- User.
- News submission.
- Prediction.
- Model version.
- Report.
- Audit log.

### 6.2 Data Retention

Prediction history should be retained for academic demonstration and user review. If privacy requirements are added, the system should support deletion or anonymization of user submissions.

### 6.3 Data Validation

- Email must be unique and valid.
- Password must satisfy minimum strength.
- News text must not be empty.
- News text must not exceed configured maximum length.
- URL must be valid if URL submission is enabled.
- Prediction confidence must be between 0 and 1.

## 7. API Requirements

### 7.1 Core Endpoints

| Method | Endpoint | Description | Auth |
|---|---|---|---|
| POST | `/api/auth/register` | Register user | No |
| POST | `/api/auth/login` | Authenticate user | No |
| GET | `/api/auth/me` | Get current profile | Yes |
| POST | `/api/predictions` | Submit news for prediction | Yes |
| GET | `/api/predictions/history` | Get current user's prediction history | Yes |
| GET | `/api/predictions/{id}` | Get prediction detail | Yes |
| GET | `/api/admin/analytics` | Get admin dashboard metrics | Admin |
| GET | `/api/admin/models` | List model versions | Admin |
| POST | `/api/reports` | Generate report | Yes |

### 7.2 Prediction API Contract

Request:

```json
{
  "input_type": "text",
  "content": "News article text to analyze"
}
```

Response:

```json
{
  "submission_id": 1,
  "prediction_id": 1,
  "label": "fake",
  "confidence_score": 0.91,
  "explanation": "The article contains patterns associated with unreliable news content.",
  "model_version": "tfidf-logreg-v1"
}
```

## 9. Acceptance Test Summary

Minimum acceptance tests:

1. A user can register and log in.
2. A user can submit news text.
3. The system returns a fake/real prediction with confidence.
4. The prediction is stored in the database.
5. A user can view their prediction history.
6. A user cannot view another user's prediction history.
7. Admin can access analytics.
8. Non-admin user cannot access admin analytics.
9. The model evaluation metrics are documented.
10. The system handles empty input and invalid URLs correctly.
